# Research 独立应用与前端展示方案

建议将新版 Research 建设为 AutoRAG 的独立配套应用，面向本地论文的比较、证据审阅和研究决策。它拥有自己的前端、API、后台任务、数据库、配置和发布流程。主系统继续提供终端检索与问答，双方首版只共享只读论文来源，不互相启动，也不调用对方完成核心功能。

该方案优先满足故障隔离和独立交付，再实现可以实际使用、可以现场演示的研究工作流。本文为方案，不表示隔离、前端或新增研读能力已经实现。本次只新增说明文档，不修改代码、配置、依赖或运行中的服务。

**当前已有隔离与实际耦合**

当前 Research 有独立服务入口和工作目录，普通 CLI、MCP 并不必然启动 PostgreSQL 与 DBOS；这部分基础可以继续利用。但以下耦合仍然存在：

- 根 package.json 同时声明主系统与 Research 的运行依赖，根构建命令包含 src/research/index.ts。
- src/research/runtime.ts 直接引用主系统配置、AutoRAGLite、索引存储和模型解析实现。
- src/research/index.ts 同时启动 HTTP、任务执行和文件监控，API 与重任务仍在一个进程里。
- 现有“AutoRAG：调试 TUI”组合配置联动启动 Research；独立 TUI 配置虽已存在，默认展示仍容易让两者混用。
- 独立目录和进程不能隔离共享的 embedding daemon、模型配额、CPU、内存和磁盘开销。

因此，不能把当前状态直接描述成“完全隔离”。新版需要以明确的依赖和运行边界交付。

**独立程度与仓库选择**

优先选择独立仓库或独立项目目录，维护 Research 自己的 package.json、锁文件、TypeScript 配置、镜像与测试。它在产品上属于 AutoRAG 的配套模块，在构建和部署上独立。独立应用不要求拆成大量微服务：一个前端、一个 API 进程、一个 Worker 进程和一个专用 PostgreSQL 实例即可。

若以后决定保留同仓，也必须成为独立子工程，明确排除在主系统的依赖解析、构建、类型检查和发布产物之外。仅在 src/research 下继续堆文件，不能实现这种边界。考虑当前根构建已经耦合，独立配套项目更容易先在不改主系统核心的情况下开展建设。

现有根依赖和旧入口是否清理，应作为单独、可回归验证的兼容性任务处理，不与新界面和算法改进混在同一轮。现有研究数据的迁移需要备份和兼容方案，不能直接重建当前数据库。

**隔离约束**

| 边界 | 目标规则 | 验证方式 |
| --- | --- | --- |
| 源码 | 主系统不导入新版 Research；Research 不深层导入主系统 src 内部实现 | 独立构建，检查导入边界与主系统变更清单 |
| 依赖 | Research 的前端、DBOS、数据库依赖及升级留在自己的工程 | 不改主系统锁文件即可安装、构建 Research |
| 启动 | 两个应用各自启动和停止，主系统默认不启动 Research | 关闭 Research 后主系统正常启动和问答；主系统关闭后 Research 可完成项目任务 |
| 数据 | Research 有专用 PostgreSQL、数据卷、缓存和迁移；主系统配置、索引、记忆不挂入可写路径 | 对照挂载和数据库权限；运行前后核对主系统状态文件摘要 |
| 来源 | 原论文目录只读，解析、导出、笔记写入 Research 自己的状态目录 | 用只读挂载验证修改被拒绝；主系统原文未改变 |
| Agent | 独立 Pi 会话、工作目录、资源加载和模型配置 | 不加载主系统会话、记忆或全局项目扩展；不同任务上下文不串联 |
| 运行 | API 不执行解析或模型推理；Worker 有并发、CPU、内存、磁盘和请求预算 | 重任务与故障注入时观察 API 和主系统表现 |
| 发布 | 新版 Research 独立构建、发布和回滚 | 回滚 Research 不修改主系统文件或数据库 |

共享物理机器上的磁盘、内存带宽或网络仍可能产生竞争。Docker 默认也不限制容器资源，应实际设置并检查限额，不能把“用了容器”当作性能隔离证明。[Docker 官方资源约束文档](https://docs.docker.com/engine/containers/resource_constraints/)

如果要求两套模型推理的性能严格独立，需要独立计算资源或独立服务容量。共享同一个模型账号时，还要核对是否共用请求和 token 配额；换成两个进程或两个 API key 不必然得到独立配额。

**首版部署和依赖关系**

浏览器访问 Research 的同源入口。API 负责静态页面、业务请求、事件流和受控论文预览；Worker 负责 PDF 解析、Pi 研读与校验；二者通过 Research 的数据库和持久任务交接。

AutoRAG 不位于这条请求路径上。Research 不请求终端 RAG 生成比较表，不借用它的聊天上下文，也不依赖它的正在运行的索引服务。新增论文的导入和目录观察由 Research 自己处理。

生产形态可以是三个容器：research-api（同时提供已构建网页）、research-worker、research-db。开发时前端使用 Vite，通过代理连接自己的 API。通过开发容器的端口转发打开网页，不需要把数据库暴露给宿主机或浏览器。

现有 API 会拒绝浏览器 Origin，不能只加网页就直接使用。新 Research 入口需要明确的同源与本地访问策略，支持 PDF 读取需要的请求方式，并通过已登记 asset ID 定位原文，不接受浏览器任意传入本地文件路径。

**如何在隔离要求下复用现有成果**

优先迁用当前 src/research 内部的业务设计和实现：文件指纹、论文与资产身份、请求幂等、阶段恢复、取消防护、证据校验、结构化阅读结果以及对应测试。迁用到独立项目后，代码在 Research 工程里维护，保留适用的版权和许可证信息。

主系统内部工具只能通过固定版本的公开接口或 Research 自己的适配实现使用，不能引用诸如 ../cli/config.ts、../core.ts、../agent/* 的源码路径。首版不为了复用而先推动主系统抽象改造。少量稳定工具的局部迁用，比把整个主系统作为活跃源码依赖更符合本次隔离目标。

Pi SDK 直接作为 Research 的固定版本依赖使用。它负责 Agent 会话和工具，不要求启动 AutoRAG。[Pi SDK 文档](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/sdk.md)

首版围绕用户明确选择的 3 至 5 篇论文进行按需解析和阅读，不强制全库向量化，也不调用主系统的 MinSync daemon。跨论文比较可以先读取所选论文的相关章节与文本证据。大规模库检索确有需要时，再增加 Research 专属索引或 embedding 服务；不自动发现或启停其他应用的服务。

**前端以研究成果为中心**

| 页面 | 用户操作 | 可见成果 |
| --- | --- | --- |
| 项目入口 | 创建研究问题，填写约束，选择论文与比较维度 | 明确的研究范围、输入状态与下一步操作 |
| 比较工作台 | 查看矩阵，筛选缺失项，选择某一格补证或重新抽取 | 各论文在同一维度上的事实与适用条件 |
| 证据审阅面板 | 打开原文，查看引用上下文，接受或修正抽取结果 | 经过人工确认的事实、修订记录和待查问题 |
| 决策与任务面板 | 生成备忘录、查看版本差异、取消或重试任务 | 可导出的研究成果与真实执行状态 |

主工作区建议采用左侧项目导航、中间比较矩阵、右侧证据阅读面板。任务状态放在底部或抽屉中，不强迫用户阅读 Agent 的完整对话日志。单元格应直接区分“有证据”“未报告”“解析不可靠”“待审阅”，并支持跳转原文。

不能只用一个模型自评置信度代替这些状态。界面也不应以流式思考文本充当进度：显示已解析几篇、已完成几个维度、当前排队原因、错误原文和下一步可做的操作即可。

当前证据绑定解析文本偏移；准确的 PDF 页面高亮还需要页码和文本位置映射。首轮可以先交付可靠的文本证据定位与原文预览，有可靠映射后再提供 PDF 精确高亮，不能显示未经验证的跳转位置。

**可以演示的完整业务流程**

用户建立“为本地 RAG 选择一种适合小预算复现的改进方法”的项目，选择三篇论文。系统按数据需求、训练成本、评测集合、质量指标、延迟和代码可用性抽取结果。

比较矩阵中，每个结论都有来源。若两篇论文的分数看似一高一低，但数据集或模型规模不同，系统展示“条件不同，暂不据此排名”，并列出具体条件和出处。缺失信息保留为缺口，不让模型补出合理数字。

用户检查证据，修正一个单元格。重跑时，模型的新建议与人工确认值并列，不能静默覆盖。随后生成有依据的决策备忘录，包含候选方法、选择理由、未解决问题和下一步最小实验。

导入第四篇论文后，只对它及依赖相关事实的比较项进行更新评估，提出对旧备忘录的修改建议，用户确认后生成新版本。无需原 PDF 内容变化，也能形成有意义的增量研究流程。

前端价值在于同时管理这些对象，并让用户直接纠正细节。Open Paper 已实现项目和抽取表格，说明这个交互方式具有参考实现；当前产品应进一步突出条件核验、修订保留和决策更新，而不宣称表格或论文聊天本身是原创。[Open Paper](https://github.com/khoj-ai/openpaper)

**技术选型与职责**

| 部分 | 建议技术 | 选型理由 |
| --- | --- | --- |
| 页面 | React、TypeScript、Vite | 适合本地交互工作台；独立于主系统构建，不引入不必要的服务端渲染 |
| 服务端数据 | TanStack Query，必要时使用 TanStack Table 管理矩阵 | 管理异步读取、局部刷新、编辑后的缓存失效与表格状态 |
| 原文预览 | PDF.js | 原文阅读和证据对照，验证页面定位能力后逐步增加高亮 |
| API | Node.js 24、Fastify 5、TypeBox | 延续已有能力，以模式校验形成清晰 API 契约 |
| 持久化 | 专用 PostgreSQL 实例与业务 schema | 项目、证据、审阅、版本和事件具有较强关系约束 |
| 后台流程 | DBOS 加应用级任务状态 | 复用阶段恢复和持久队列，避免另外引入 Redis 或 RabbitMQ |
| 模型运行 | 固定版本 Pi SDK | 显式配置资源、工具、会话与取消，构建面向论文的领域运行时 |
| 状态推送 | SSE 加查询接口 | 单向推送阶段与结果，修改走 HTTP；重连时可恢复或重取 |
| 隔离 | Docker Compose、资源限额、只读来源挂载 | 独立启动、故障边界和资源开销约束 |
| 验证 | Vitest、真实 PostgreSQL 集成测试、浏览器 E2E | 验证业务一致性、恢复和用户流程；前端测试工具在实施前再确认 |

技术的新颖性主要来自 Pi 领域运行时、可恢复任务、证据契约和可修订成果的组合，而不是增加框架数量。版本在实施时锁定；不把所有最新上游 API 都当成当前依赖版本已经支持。

DBOS 官方提供 API 服务通过 DBOSClient 向独立 Worker 入队的示例，可参考这一边界。本项目当前 API 与 Worker 的同进程实现需要改造，不能视为现成能力。[官方模式说明](https://docs.dbos.dev/typescript/examples/queue-worker)，[GitHub 示例](https://github.com/dbos-inc/dbos-demo-apps/tree/main/typescript/queue-worker)

**后端流程与一致性**

接收研读请求时，API 校验项目和来源范围，在同一业务事务里保存请求幂等记录、冻结输入版本、任务以及待派发标记。提交成功后返回任务 ID。Worker 从持久任务派发 DBOS 流程，使用稳定 workflow ID 去重；派发后进程中断，也能再次检查待派发记录，不让业务任务静默丢失。不直接写 DBOS 内部表。

工作流依次完成来源校验、解析、事实抽取、证据验证、条件核验和结果提交。可采用“逐篇抽取后汇总比较”的有界流程，初始模型并发为 1。角色分工不必等于多个模型或多个并行 Agent。用户手动补证优先于后台批量任务。

结果提交和业务事件在同一事务落库。SSE 消费这些已提交事件，客户端按事件 ID 去重；历史事件过期或重连存在缺口时，重新读取任务和成果快照。数据库是状态依据，推送不是唯一存储。

取消需要持久标志、正在运行的模型调用的 AbortSignal，以及提交前检查。后台流程取消不自动意味着远端模型立即停止计费。DBOS 官方也区分工作流取消与正在运行 step 的中断；具体接口必须匹配安装版本。[取消语义](https://docs.dbos.dev/typescript/tutorials/workflow-management)

进程可能在外部模型已返回、结果尚未提交时中断，因此不承诺模型调用严格只执行一次。应承诺的是业务结果不重复、已提交阶段可复用、迟到结果不覆盖已取消或较新版本，以及用量和失败原因可追踪。

比较项保存 AI 建议与人工确认结果的不同版本。编辑请求携带版本条件，发生冲突时返回明确提示。缓存键包含文件内容和解析版本、研究问题、维度、模型配置及抽取协议版本，避免维度改变后错误复用旧结果。

**数据库中的核心对象**

Research 继续维护论文、资产版本和证据，增加项目、比较维度、单元格版本、比较判断、人工审阅和备忘录版本。任务和事件独立保存，DBOS 系统状态由 SDK 管理。

其中三种状态不能混为一谈：Pi 会话保存模型上下文；业务任务保存执行进度；研究成果保存用户长期使用的事实和判断。关闭网页不删除任务，清空模型会话也不删除人工确认的比较表。

证据验证分成“原文存在”和“原文支持结论”两层；前者可以使用规范化文本匹配等确定性方法，后者需要语义核查与标注评测。实验条件是否可比是第三层问题。[ResearchQA 论文](https://arxiv.org/abs/2607.11074)与[评测实现](https://github.com/khoj-ai/openpaper/tree/master/server/evals)提供了区分引用指标与答案质量指标的参考，但其单论文评测不能直接覆盖跨论文决策。

**资源策略**

默认不扫描和研读全库。用户选择少量论文后按需处理，未启动 Research 时没有其后台任务。对 Worker、API 和数据库分别设置限额，并评估三者合计的开销，而不是只约束 Node 进程。

Worker 需要文件大小、页数或解析时间、模型请求次数、输入长度和任务总预算限制；错误时保存已完成成果并允许局部重试。资源配置根据开发机的空闲容量实测决定，不在方案里编造固定 CPU 或内存就足够的保证。

模型配置由 Research 自己管理，通过环境变量、密钥文件或其他已支持的凭据引用读取，浏览器拿不到凭据。正文是否可发送到远端模型仍需受可信配置的显式授权。演示示例不能将授权自动推广到用户私人论文。

**分阶段范围与退出条件**

| 阶段 | 交付 | 完成条件 |
| --- | --- | --- |
| A 独立骨架 | 自己的工程、配置、启动、数据库与 API/Worker 边界 | 双方可各自关闭、构建和运行；Research 不写主系统状态 |
| B 使用闭环 | 3 至 5 篇论文、5 至 8 个维度、矩阵、证据审阅、人工修改与导出 | 用户可完成一次真实比较任务；证据位置可核对；重跑不覆盖已确认编辑 |
| C 可交流成果 | 条件核验、备忘录、一次新增论文更新，以及恢复与性能证据 | 可演示错误比较的识别、修改建议、Worker 中断恢复及主系统回归结果 |

第一轮不做多人协作、自动执行陌生仓库、全网自动追踪、全库知识图谱或第二套工作流框架。复现准备度报告可以后续追加，前提是前面的闭环确实节省研究整理时间。

**面试演示与技术交流**

准备三篇可分发、来源明确的示例论文和一个有实际约束的研究问题。演示沿着一条故事线进行：建立项目并看到真实任务进度，点击单元格查看原文，解释一次条件不一致的比较，修正事实并导出备忘录，新增论文后审阅修改建议。

再补一个工程演示：停止自己启动的 Worker，API 仍能查询旧成果；重启后任务从已提交阶段恢复。同时展示主系统的独立运行与回归记录。中断演示只在专用测试数据和本次应用进程上执行。

可另备明确标注的示例数据模式，用来在模型服务不可用时展示已保存成果和交互，不能将回放伪装成实时推理，也不能用示例数据证明真实模型质量。

| 面试问题 | 应解释的实现 | 最好展示的证据 |
| --- | --- | --- |
| 为什么独立做这个模块 | 研究成果需要长期修订；主 RAG 以即时问答为主 | 同一任务在两种流程下的操作和成果对照 |
| 如何确保不拖慢主系统 | 无运行依赖、独立状态、按需解析、资源限额、无共享推理队列 | 依赖关系图、容器限制和并发时性能记录 |
| Pi 二次开发在哪里 | 明确资源加载与工具范围，提交有模式约束的结果，管理上下文和取消 | 一次工具调用与事实到证据的关联记录 |
| 为什么要持久工作流 | 解析与模型请求是长任务，存在崩溃和重试窗口 | Worker 中断与恢复，外部模型请求可能重放的边界说明 |
| 怎样防止重复和覆盖 | 幂等键、稳定任务 ID、结果唯一约束、版本检查和人工确认状态 | 重复点击、迟到结果和并发编辑测试 |
| 如何评价 AI 结果 | 原文存在性、语义支持、条件可比性分开评测 | 标注样本、失败案例及可重复评测脚本 |
| 为什么没有再引入更多框架 | 当前规模用 PostgreSQL 和 DBOS 已足够 | 可运行的单机部署与实际处理规模 |

**隔离和质量的验收证据**

需要验证关闭 Research 数据库、Worker 崩溃或解析大 PDF 时，主系统仍能正常启动和回答；Research 的安装、构建与模型配置变化不修改主系统依赖和配置。运行前后核对主系统配置、索引和记忆文件，确认无非预期写入。

性能比较至少包括 Research 关闭、空闲、解析中和模型调用中四种状态。固定模型、论文、问题、缓存条件，并区分本地操作耗时与提供商网络波动。预先约定可接受的退化阈值，实测后再讨论是否满足，不直接宣称零影响。

质量评测同时比较当前终端 RAG 和简单的直接读论文方案，记录引用正确性、应拒答问题、可比性误判、人工纠错量、完成比较任务的时间和模型用量。所有性能与质量数字应来自可复查的真实运行。
