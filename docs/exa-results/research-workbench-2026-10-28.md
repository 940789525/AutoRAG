# Research 论文研究工作台改进分析

建议将当前“增量论文研读收件箱”发展为“证据驱动的论文比较与研究决策工作台”。核心使用场景是：围绕一个真实研究问题，选择少量本地论文，整理可核查的比较事实，辨别结果是否可比，形成能够持续修订的选型或复现决策。

现有终端 RAG 继续承担资料检索和即时问答；Research 围绕长期研究项目维护证据、比较结果与人工判断。前端的价值是同时呈现表格、论文原文和审阅记录，减少反复打开文件、抄录数据、核对上下文的工作。

本文为理论方案。所述新增能力均为规划，不表示当前已经实现，也不表示其质量或性能已经得到验证。研究截至 2026 年 10 月 28 日；近三个月指 2026 年 7 月 28 日至 10 月 28 日。

**为什么当前收件箱容易显得用处有限**

当前流程围绕“新文件出现”展开，但实际研究需求通常围绕“一个问题尚未解决”展开。论文没有发生变化，研究者仍然会重新比较方法、更换实验约束、增加评测维度、修正旧理解。只在导入时生成一张阅读卡片，无法充分承接这些工作。

当前代码已经具有论文、资产版本、主题、任务、证据片段、阅读卡片、反馈、幂等请求与恢复能力。PaperNote 也已有 comparability 字段。问题并非完全没有比较功能，而是比较主要作为一张自动笔记中的概括性结论存在，尚未形成逐项事实、比较条件、人工修订和决策依据之间的完整联系。当前 Evidence 的定位是解析文本 start/end，不含完整 PDF 页面坐标；网页精确高亮需要补建映射，不能只增加一个 PDF 播放区域就宣称已完成。

此外，初始全库索引会延迟首篇论文可用时间。研究工作台应允许用户先围绕选中的一篇或几篇论文开展结构化阅读，全库向量检索在需要时参与。具体可跳过哪些索引步骤，需要结合解析器和现有检索依赖验证。

**与终端 RAG 的产品边界**

| 维度 | 现有终端 RAG 的主要用途 | 建议的 Research 工作台 |
| --- | --- | --- |
| 入口 | 提出一个检索或解释问题 | 建立研究项目，选论文，设比较维度和目标约束 |
| 主要成果 | 一次对话中的答案与来源 | 持久的证据矩阵、审阅记录、决策备忘录 |
| 使用过程 | 搜索、阅读、追问 | 对照、查证、纠正、补证、做决策 |
| 反馈方式 | 在下一轮对话中补充要求 | 对具体单元格、证据和判断作结构化修订 |
| 更新方式 | 重新提问 | 新论文或新维度触发局部重算，并展示对结论的影响 |
| 完成标准 | 当前问题得到回答 | 关键维度证据充分，缺口清晰，选型理由能追溯 |

这不是说终端不能比较论文。差别在于研究成果能否跨会话保存、逐项编辑、关联原文，并在补充资料后继续演进。

**建议形成的实际使用闭环**

以“在有限显存和开发时间下，为本地 RAG 选择一种适合的改进方法”为例。用户选择 3 至 5 篇论文，填写自己的约束，并选择训练需求、评测数据、检索质量、延迟、代码可用性等维度。

第一步，生成可编辑的证据矩阵。每个单元格保存抽取结果、原文证据、适用条件和核验状态。没有提及的信息标为“未报告”，表格解析失败标为“未可靠提取”，不能让模型补出一个合理数字。

第二步，核验比较条件。例如论文 A 的准确率高于 B，但二者数据集、模型规模、训练资源或评测口径不同。系统应把比较标为条件不一致，展示差异来源，而不是自动判定 A 更好。两篇论文出现不同数字，也不自动等于科学结论矛盾。

第三步，呈现证据缺口并允许补证。例如当前无法确定离线可用性，用户可以选择查看方法章节、补充附录、关联官方代码仓库，或保留“无法判断”。Agent 的后续动作针对这个缺口，不必对整库再研究一遍。

第四步，用户审阅并修订单元格。界面区分“作者报告的事实”“系统推断”“用户判断”；系统重跑不能覆盖用户已确认的判断。修改留下依据、版本与审阅记录。

第五步，形成选型或复现决策备忘录。内容包括推荐候选、适用条件、替代方案、未解决问题和下一步实验。推荐属于有约束的建议，不宣称通过阅读就证明了真实实验效果。

第六步，用户后来导入新论文，系统展示它对当前项目哪些维度可能有影响。只有受影响的单元格和决策段落进入待更新队列，旧版本仍可查看；最终结论由用户确认。

这里的“增量”来自论文集合、研究问题、比较维度和人工判断的变化，不依赖原始 PDF 自身经常变化。文件收件箱可以保留，作为项目的候选论文入口。

**应优先实现的三个产品模块**

1. 项目与比较矩阵：研究问题、目标约束、论文集合、少量自定义维度、持久单元格和 CSV 导出。这是工作入口。
2. 证据阅读与审阅：点击单元格查看原文，核查实验条件，接受或修正抽取结果，维护待补证清单。这是质量保障。
3. 决策成果与增量更新：由已确认事实生成备忘录，记录版本，新增论文时展示影响和局部更新。这是比一次问答更长久的价值。

前端可以采用“比较表格为主视图，右侧原文与证据面板，单独的任务状态区域”。聊天是补充入口。任务状态应来自后台真实事件，显示当前阶段、已处理论文数、等待原因、失败信息和取消操作。

**Pi 二次开发应体现在哪里**

建议继续通过 SDK 嵌入 Pi，构建领域工具。例如读取指定论文的章节、在指定来源内查找证据、提交有模式约束的抽取结果、提交待核查比较条件。这些是拟新增的工具契约；当前 reader 的主要模式仍是受限上下文加结构化提交，不能当作已有完整领域工具。

执行顺序和预算由后端控制：选定来源、准备文本、调用受限 Agent、校验结果、提交证据、更新成果。Agent 负责语义抽取和综合，后端负责文件身份、来源范围、数据约束、取消和事务。既不把整个流程写成一个无限自主对话，也不需要为了展示多 Agent 而默认并发多个模型。

建议分开管理三种状态：Pi 管理一次研读的会话上下文；DBOS 管理业务任务阶段和恢复；PostgreSQL 管理证据、审阅与成果版本。浏览器断开后后台任务是否继续，应由业务任务约定决定，不能简单等同于模型会话断开。

Pi 官方的 [pi-durable](https://github.com/earendil-works/pi/tree/main/packages/durable) 已提供持久化对话、任务和文档状态，确实值得跟踪。但 README 明确标注 Experimental，API 可能随版本变化。它和本项目现有 DBOS 有职责重叠，不建议直接叠加；如果未来考虑替换，应先验证版本兼容、恢复语义和存储边界。

**技术栈选择及后端价值**

| 部分 | 建议 | 真实需求和可展示能力 |
| --- | --- | --- |
| 前端 | React、TypeScript、Vite、TanStack Query；论文预览采用 PDF.js | 比较矩阵、异步任务、缓存失效、原文对照和人工修订。具体版本在实施时确认，暂不为单用户本地工具引入服务端渲染。 |
| API | 复用 Node.js 24、Fastify 5 | 领域资源设计、请求校验、幂等提交、结构化错误、分页与任务接口。 |
| 数据 | 复用 PostgreSQL，增加项目、比较字段、单元格版本、证据关系与审阅记录 | 关系完整性、并发修改控制、版本管理和影响范围查询。 |
| 后台任务 | 复用 DBOS，补齐优先级与资源准入控制 | 长任务恢复、部分重试、取消、重复提交防护和可追踪阶段。资源优先级不是使用 DBOS 后自动具备的能力，需要实际实现。 |
| Agent | 复用 Pi SDK，增加领域工具和结果验证 | 会话生命周期、上下文边界、工具范围、模型预算和结果协议。 |
| 检索 | 复用本地 MinSync、现有解析和证据读取 | 选中论文直接阅读与项目范围检索协作；大库需要检索，单篇首次使用不应被无关论文的索引阻塞。 |
| 实时交互 | 延续 SSE，配合状态重取 | 后台阶段推送、断线重连和事件恢复。审阅修改可以走普通 HTTP，暂不需要协同编辑协议。 |
| 可观测性 | 先记录结构化阶段耗时、任务链路和实际用量；有跨进程排障需求时接 OpenTelemetry | 分开识别排队、解析、embedding、模型网络和生成耗时，支持性能归因。 |

技术栈是否新，不等于项目是否有价值。这套组合已经能覆盖现代 TypeScript 后端、异步工作流、关系数据库和 Agent 应用工程；面试说服力来自这些技术解决了哪些实际失败场景，以及结果如何验证。

暂不引入第二套 Agent 编排框架、第二套工作流系统、图数据库或分布式微服务。支持关系、来源关系和影响关系可以先存 PostgreSQL；只有实际查询复杂度证明有必要时，才讨论专用图系统。

**数据库与一致性的关键问题**

业务对象可以在现有 paper、asset、topic、run 和 evidence 基础上扩展为 project、dimension、cell_revision、claim_evidence、comparison_assessment、review、artifact_revision。重点不是表的数量，而是保留以下联系：某个项目维度的事实来自哪个文件版本的哪段文字；比较结论适用哪些条件；哪个判断由用户确认；哪个成果版本引用了这些判断。

事实和判断应分开存储。单篇论文报告了什么，可以作为版本绑定的事实；它是否适合当前项目，是依赖目标约束的判断。用户改了目标约束，不必重新解析原文，但需要重新评估相关建议。

抽取缓存也不能只按文件 hash 复用。缓存键至少需要考虑解析版本、抽取模式、提示与模型配置；项目相关抽取还依赖问题和维度。人工修订需要乐观并发版本，避免后台重跑静默覆盖用户编辑。

恢复执行不等于模型请求严格只执行一次。进程可能在远端模型返回、结果尚未提交时中断，重试仍可能再次计费。能够承诺的是已提交阶段复用、业务结果幂等、取消后不发布过期成果，以及实际用量和错误可见。

当前服务会拒绝浏览器 Origin，开发容器内部 loopback 也不是 Windows 浏览器的 localhost。实施网页时必须设计同源服务或代理、VS Code 端口转发与后端访问方式；只添加前端页面无法打通。原文预览应通过已登记 asset ID 解析授权文件，不接受浏览器任意传入本地路径。

正文仍按既有 trusted-config 授权决定是否可以发送给远端模型。网页不能自行切换到远端处理，也不能接触数据库或模型凭据。

**适合分期交付的范围**

第一阶段先完成一个可用闭环：一个项目、3 至 5 篇 PDF、5 至 8 个比较维度、逐格证据、人工修正、CSV 或 Markdown 导出。优先使用可可靠抽取文本的 PDF，表格和图像无法可靠处理时明确留空。首篇可用时间和普通 RAG 性能回归必须同时记录。

第二阶段增加比较条件核验、证据缺口、成果版本和新增论文影响提示。允许用户控制补证次数和模型预算。这个阶段形成更清晰的差异化，但应先验证第一阶段是否真能替代手工整理工作。

第三阶段再试“复现准备度分析”：核对官方代码、公开数据、环境与资源要求，形成最小实验计划。Paper2Agent 展示的是把方法做成经测试工具的更强目标；当前可以先做研究到复现之间的准备工作。只有用户确实需要执行，才单独设计隔离运行与结果核对能力。

外部论文订阅、自动运行陌生仓库、全自动系统综述、多人协作和知识图谱大屏不进入首轮范围。

**怎样证明值得写入简历**

建议以当前 TUI RAG 和“直接把论文交给同一个模型”的简单方案作为基线。在相同论文、模型与问题下比较，避免把更强模型带来的改善误记为系统设计收益。

质量验证至少分三层：引用原文是否存在；原文是否足以支持具体结论；比较条件是否允许推出优劣关系。机械匹配可以自动化，但不能单独证明语义正确。ResearchQA 的引用度量可借鉴；跨论文可比性、人工修订保留和增量影响还需建立自己的小型标注样本。

工程验证覆盖重复请求、取消后迟到结果、部分失败重试、进程中断恢复、编辑冲突和事件重连。性能验证记录首篇可用时间、每阶段耗时、项目成本，以及 Research 空闲或索引时普通 RAG 的延迟变化。用户价值用真实任务验证，例如整理一份五篇论文的比较表，需要多久、人工纠正多少处、最终是否帮助选出下一步实验。

简历可以围绕“Pi 领域工具与上下文控制”“可恢复的异步后台任务”“可核查且可修订的研究成果”展开。完成并实测后，可采用类似表述：

> 基于 Pi SDK、Fastify、PostgreSQL 与 DBOS 构建本地论文研究工作台，支持具有原文证据的跨论文比较、人工审阅与增量更新；实现长任务恢复、请求幂等及取消控制，并通过引用核验和性能基线评测验证系统效果。

规划中的功能不能提前写成已完成，减少耗时、准确率和成本等数字只填写实际测量结果。现有通用自动化测试通过，也不能替代新增科学研读能力的质量评测。
