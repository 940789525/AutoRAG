## 分层验证

1. 纯业务单元测试：输入摘要、失效规则、有效展示值、条件核验与预算判断。不要为简单字段赋值复制实现写测试。
2. 契约测试：请求 schema、错误码、ETag、幂等重放、事件序列及生成类型一致。
3. PostgreSQL/DBOS 集成：真实专用临时库、实际唯一约束、事务回滚、派发、进程中断恢复。测试库命名和凭据检查必须防止误连真实库。
4. 浏览器 E2E：真实 API/数据库/Worker，模型使用可识别的受控 provider；验证界面不是孤立 mock。
5. 有预算的 live 小样：真实 Pi 和模型，显式远端许可，原文授权明确。

## 关键并发与故障实验

- API 写完业务记录、返回前断连接：重试同 key 返回原响应。
- 业务事务完成、DBOS 尚未入队时停止 Worker：重启仍能派发。
- DBOS 已接收、submitted 未写入时停止：稳定 workflow ID 防止双任务成果。
- 模型返回、结果未提交时停止：允许外部重放，但业务成果唯一，费用风险被记录。
- 业务成果及事件已提交、DBOS checkpoint 尚未完成时停止：重放命中 run_outputs，引用、revision、事件数和 matrix version 均不重复。
- 用户更正期间旧模型返回：新建议可保留，人工有效值不得被覆盖。
- 项目改 revision 后旧任务返回：旧结果不能成为当前矩阵/备忘录。
- 仅保存新输入而未开始分析：已有新矩阵快照，旧结果按依赖标记过时或复用；旧 matrixVersion 仍能读取当时的精确投影。
- 同一 project revision 内更正事实或重叠修复：依赖旧值的比较立即过时，迟到发布不能恢复旧结论。
- 两个标签页分别接受不同备忘录：项目 expectedProjectETag 竞争只有一个成功，失败页面保留原草稿供比较。
- Cancel 和 publish 同时发生：锁序决定结果；已取消 run 不发布，已完成 run 取消不改终态。
- Worker、数据库、SSE 分别故障：错误语义清楚，不影响主系统；恢复后能读取持久结果。

只中断测试创建的容器/进程，禁止停止维护者的 MinSync、主系统、其他 clone 或原有数据库。

## 隔离与性能

先记录基线：代码/锁文件摘要、配置路径、专用测试 home、模型和解析版本、主机容量、其他负载、冷/热缓存。主系统 QA 严格使用临时 AUTORAG_HOME 与 AUTORAG_CONFIG；真实 home 只在确有任务需要时读取摘要，不能覆盖或“修复”。

测四种状态：Research 关闭、空闲、解析中、模型调用中。保留相同论文、问题和缓存条件。已有本地检索接口或 span 可测时，预热后每组至少 30 次；不为测速改变主系统业务代码。模型网络延迟单独报告，不混同检索时间。

初始目标在 T-00 固定：本地检索 p95 退化不超过 10%；小 fixture 下 API 查询 p95≤200ms、接受任务 p95≤500ms。它们是待验证目标，不是当前结果；硬件噪声或样本不足时结论为 inconclusive，不能直接判通过。若不达标，先收紧 Research 资源或并发、分离推理容量，再复测，不能悄悄提高阈值。

live 端到端还需记录首次可用行、完整项目、token、未知用量、失败与费用估计。外部额度不足时可完成本地隔离验证，但 live 性能与质量必须标为未验证。

## 小型质量评测

从获准的公开论文中建立冻结集：建议 6—10 篇、至少 60 个事实项、20 个比较条件案例（包含至少 12 个不应直接可比的例子）和至少 10 个应拒答/无法确定的问题。保留抽取难点，不只挑纯文本简单页面。

先人工记录预期事实、证据区间、条件及可接受替代证据，再执行系统。标注者身份与争议处理方式要说明；不能让生成模型独自决定正确答案。

初始门槛：

- 对最终展示为有依据的引文，原文匹配率必须 100%；校验失败应被拒绝或降级，不能混入已验证结果。
- 已报告事实的人工语义支持率目标≥90%，同时报告可回答项覆盖率，目标≥80%，防止靠全部拒答提高精度。
- 负例中“错误判为可比”的数量为 0；正例可比召回率单独报告，避免一律证据不足。
- 应拒答问题正确处理率目标≥90%。

这只是项目小样验收，不代表跨领域普适准确率。比较当前终端 RAG 和同模型直接读论文基线，记录提示、模型、输入预算和失败；不把模型升级收益记为架构收益。

## 验收证据格式

每份记录包含 specVersion、taskId、acceptanceIds、代码提交、模式、时间、环境、输入 manifest、命令、退出码、指标、原始错误、限制与清理回执。正文或凭据不进入公开证据，公开论文引用需保留来源。

状态只能是 pass、fail、blocked、not_run 或 inconclusive。完整 MVP 需全部 P0 的验收通过；部分通过应列出未验证项。文档格式/链接检查通过不能充当应用验收。

research-spec-v1.1 的 AC-20—26 是 P0 的补充验收，不因原 AC-01—18 已通过而省略。逐项构造反例：同输入成功重跑、失败后继并发提交、业务提交与 checkpoint 之间中断、三篇中仅两篇条件一致、模型未读段落人工补证、伪造 coverage、两草稿竞争。每例记录具体输入/成果 ID、前后版本及事件数；尚未实现时记 not_run。
