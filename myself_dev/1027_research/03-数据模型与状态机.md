# 数据模型与状态机

## 数据所有权与基本规则

全部业务数据进入专用数据库的 `research_v2` schema；DBOS 自己管理 `research_v2_dbos`。迁移只作用于专用库，不连接旧 Research 库。所有 ID 为服务端生成 UUID，时间使用 UTC timestamptz，文本偏移采用 JavaScript UTF-16 code unit，与解析文本的 slice 语义一致。

明确区分：内容不可变版本、当前展示指针、后台任务。模型会话不是业务数据库，SSE 不是状态存储。

表的物理命名可在首个迁移前统一，但业务对象和约束不能静默省略。项目、资产、单元格、比较与备忘录之间要通过复合外键或事务检查防止跨项目/跨库关联，不因 UUID 看似随机就跳过校验。

不建通用图数据库。依赖查询先使用上述外键和输入关联，必要索引包括待派发任务、项目单元格、未完成任务、项目版本与证据输入。

## 三层版本

1. project revision：问题、约束、asset 集合或维度修改后加一。旧输入保持可读；同一事务初始化该输入版本的矩阵。
2. matrix version：项目输入切换、单元格建议发布、用户审阅或当前比较有效性变化时加一，在项目内单调递增。生成备忘录绑定精确版本。
3. source revision：asset hash 加解析版本和文本 hash。路径只是位置，不是内容身份。

matrix version 变化时在同一事务写不可变 matrix snapshot，保存每格实际采用的建议、人工记录和比较输入版本。历史矩阵与导出必须按快照投影，不能从当前 cells.head 指针重新拼出旧版本。快照中的 ID 在写入事务校验同项目归属；所引用历史记录不能自动删除。

同一 asset、维度和上下文的结果允许复用，但项目相关抽取必须核对完整输入 digest。原文变化不能只改 file_location 指针继续复用旧证据。

**项目输入切换：**PATCH 锁项目并检查项目 ETag，在同一事务追加 project revision、递增 edit_version 和 matrix version、写入新 matrix snapshot。新快照只包含新版本选中的行列：依赖不变的成果标为 current 并引用原记录；受影响的旧成果标为 stale，仅供对照；没有成果的格子标为 pending。尚未分析时也必须能查询这个新矩阵，不能继续以旧快照代表新问题。

applicability=current/stale/pending 与 valueState、人工审阅状态分别表达。过时的比较和备忘录不作为当前有效输入；旧定稿指针可保留供历史阅读，查询和页面必须标记过时。历史快照保留当时的内容与状态；当前来源可用性另行返回，不回写历史快照。

项目 ETag 对应 edit_version；矩阵的后台变化使用 matrixVersion 表达，不无故使项目输入表单失效。单元格 ETag 对应 cells.version，建议发布和人工审阅都会使其递增。

## 比较范围与依赖失效

scope 固定为 `{assetIds,metricDimensionId,metricDimensionRevision}`；assetIds 为排序、去重后的 2—10 个当前项目资产。条件字段及其证据由 assessment_inputs 引用，所有参与资产均须有明确覆盖记录。全组 comparable 要求所有必需条件有据且一致；已有明确不一致为 different_conditions；没有明确差异但关键条件缺失为 insufficient_evidence。不能用其中两篇的证据替整组作肯定判断。

state 是当时的比较结论；validity=current/stale 是根据当前输入依赖计算的有效性，不能把 stale 改写成“证据不足”来丢失历史。人工更正、拒绝、采用新建议或来源变化后，同事务把依赖旧有效值的比较从当前有效集合移出、递增矩阵版本并写快照；关联备忘录立即显示过时。不自动调用模型，用户显式提交 repair 后才重新核验。

比较开始时冻结实际 cell/review 输入向量。发布时锁项目和相关单元格，并检查该向量仍是当前有效输入；否则拒绝成为当前成果，run 置 superseded，已完成的其他成果保留。并行分析/修复的作用范围必须入快照，不能只检查 project revision 就认为输入仍有效。

## 任务状态

`queued -> running -> succeeded | failed | cancelled | superseded`。

- 分析 phase 为 `validate_source / parse / extract / verify / compare / publish`；登记任务使用 `observe / hash / register`，备忘录任务使用 `prepare / synthesize / verify / publish`。
- cancel_requested_at 是独立持久标志。运行中先显示“正在取消”，确认不再发布结果后才成为 cancelled。
- superseded 表示任务的项目或成果输入已过时，不能发布为当前结果。
- 不把缺失字段当作任务失败。结构合法的 `insufficient_evidence` 可以成功返回。
- 真正的解析/模型失败标为 failed，已提交的其他单元格保留，暴露 partial_results；不能展示整份分析成功。
- retry 创建新 run 和 generation，关联 failed/cancelled 的原 run，复用仍有效的完成成果；成功任务用显式 rerun，superseded 任务改用当前输入提交，均不抹除旧记录。

## 事务边界

**提交任务：**先检查已存在的幂等请求；新请求锁项目、检查输入版本、冻结配置与来源范围，写 run、pending 派发标志、事件 seq=1 和响应。input_snapshot 保存实际使用的资产、问题/维度版本、模型/提示/解析配置及预算，不能只存摘要。相同语义输入的任务按下表处理；新 generation 在项目锁内分配。所有写入同一事务完成后返回 202。

| 操作及已有最新任务 | 行为 |
| --- | --- |
| 相同 Idempotency-Key 与请求 | 重放原响应，不再分配 run/generation |
| analyses/memoranda 提交，相同输入 queued/running | 返回活动 run，即使 rerun=true 也不并行重复消费预算 |
| 相同输入 succeeded，rerun=false（默认） | 返回已有成功 run，不调用模型 |
| 相同输入 succeeded，rerun=true | 创建新 run，generation 加一；submission_kind=rerun，重新授权本次预算，不直接复用被要求重算的模型结果 |
| 相同输入 failed/cancelled，直接提交 | 409 并返回 existingRunId；由专用 retry 操作创建新 run/generation |
| failed/cancelled 的 retry，且原输入仍有效 | submission_kind=retry、retry_of_run_id 指向原任务；如已有活动后继则返回该后继 |
| superseded 或原输入已失效 | retry 返回 409；取得当前输入后重新提交，不能静默换题或反复执行旧输入 |
| 最新任务 superseded，用户从当前项目重新提交分析 | 校验当前输入，重新冻结目标格版本和人工输入，再创建下一 generation；submission_kind=initial，不复制过时快照 |

首次 generation=1、submission_kind=initial。分析 input_digest 覆盖项目输入版本、分析模式/资产范围、模型/提示/解析/预算配置及当前人工输入版本；备忘录另包含 matrixVersion 与 baseId。不包含幂等键、generation、rerun 控制位和目标格的并发校验 version，任务自己发布的建议不会改变原分析的语义身份。比较阶段再冻结所用的 cell/review 输入向量并保存到成果记录。

retry 保持原模型/提示/预算等语义快照，配置变化按新输入提交，不暗中切换；目标格并发 version 在新 run 认领时重新冻结。已完成成果仅在 dependency_digest 和当前有效指针匹配时复用，并在新 run_outputs 中登记对原资源的引用，不再发布一次。输入或人工记录已变则拒绝 retry。每个 retry_of_run_id 至多一个后继（唯一约束）；旧 run 再次被 retry 时返回已存在的后继，即使后继已终态也不再分支，要继续恢复须对该后继操作。

**派发：**Worker 认领 pending/租约已过期的记录，短事务设置 lease，提交后通过 DBOS SDK 入队。workflow ID 固定为 `research-v2:<run-id>`。收到确认再设置 submitted。重试不能随机换 workflow ID。单 Worker 首版也要测试“已入队但未标记”的恢复窗口。

**发布单元格：**锁 run 和相关项目/单元格，确认未取消、project revision 有效、资产未失效，再追加 cell revision、证据关系和业务事件，更新指针与 matrix version。模型建议永远不直接改 reviews。同一 project revision 内重叠的分析/修复冻结目标格 version；迟到成果若与启动时版本不符，不覆盖当前建议，而将该 run 置 superseded，用户修订后的旧建议仍可作为历史保留。

**阶段成果去重：**数据库事务同时写 run_outputs、具体业务成果、展示指针、matrix snapshot 和事件。output_key 使用稳定逻辑标识，例如 `cell:<assetId>:<dimensionId>:<dimensionRevision>`、`assessment:<scopeDigest>`、`memorandum:draft` 或 `registration:<fileId>`，不含随机 ID、尝试次数或新分配 revision。重放先查该键，已存在则返回原 resource_refs，不再次追加 revision/事件或递增 matrix version；结果不同也不覆盖首次提交。唯一约束冲突后读取获胜记录，事务外不提前发布事件。DBOS workflow ID 和 (cell_id,revision) 不能替代此业务约束。

**用户修订：**锁项目与单元格并核对 If-Match；追加 review、更新有效展示指针、matrix version 和对应快照，在同一事务中完成。更正论文事实需要 evidence，用户判断显式标记。重跑只产生新建议，不丢弃旧 review。

所有需要同时锁这些对象的事务统一采用 project → run（如有）→ cell（按 ID 排序）的顺序；cancel/publish 对同一 run 串行。不能让提交锁 project 再锁 run，而发布反向锁造成恢复期间死锁。

**备忘录：**绑定已读取的 project revision、matrix version、cell/review/assessment 输入。发布前再次校验；输入变化则任务 superseded，不更新当前草稿/定稿指针。用户接受版本另行提交，模型不能自行接受。

**接受定稿：**锁项目，在同一事务校验备忘录 If-Match、请求的 expectedProjectETag，以及 project revision、matrix version 和来源有效性。通过后更新 accepted_memorandum_id 并递增 edit_version；两个标签页接受不同草稿只能有一个按原项目 ETag 成功。仅校验各自草稿的 ETag 不足以保护同一个定稿指针。幂等请求重放仍优先于 ETag 检查。

## 人工审阅与有效展示值

AI 建议与人工记录分别保存。已确认/更正的事实默认仍显示人工版本，新建议显示“待比较”，用户可以保留旧值或接受新建议。若来源版本改变或维度语义改变，保留历史人工记录并标记 stale，不继续称为当前已验证事实。

后台任务不能批量把全部单元格重置为未审阅。只对输入依赖变动的项目项提出失效或更新建议。

## 增量与缓存

抽取缓存键覆盖 asset hash、parser/text 版本、问题与约束摘要、dimension revision、模型配置、提示和结果 schema 版本。结果的 dependency_digest 覆盖这些实际依赖，区别于整个 run 的 input_digest；单篇抽取不读取其他论文时，单纯增加论文数量不使旧行失效。若结果实际读过其他论文或用户判断依赖论文集合，须加入对应依赖。比较缓存另包含 scope 和所使用的 cell/review revision 集合；备忘录另包含矩阵版本。

新增第四篇论文时，新建 project revision，可保留旧论文不变的事实建议和人工记录；计算新论文单元格，重新评估有关比较与备忘录。改变问题、维度或数据来源可能触发全量项目级失效，不能一律宣称只算新增行。

## 取消、恢复和保留策略

取消与发布锁同一 run 行，决定先后顺序：先取消则不得发布，先发布并成功结束则取消返回已有终态。跨进程取消通过数据库状态轮询和模型 AbortSignal 传播；即使远端仍返回，提交门禁也拒绝迟到结果。

进程中断后 DBOS 可重放未提交阶段，外部模型请求可能再次计费。只承诺业务结果幂等，不承诺远端调用 exactly-once。失败的模型步骤默认不自动无限重试。

幂等记录保留 7 天；SSE 历史至少保留 7 天且最近每 run 1000 条，清理时保留终态和快照。项目、证据与人工记录首版不做自动删除。备份同时包含业务 schema、DBOS schema 和解析缓存，详见 09。
