# 演示与简历

## 项目定位

可以这样解释项目用途：

> 在已有终端 RAG 旁，我设计一个独立运行的论文研究工作台。它把临时问答延伸为有原文依据、可人工修订的比较和决策成果，并通过独立状态与资源边界避免研究任务拖累主系统。

当前只是规格，不使用完成时态。既有 AutoRAG、Pi 和迁用实现要注明来源；个人贡献聚焦新版模块的设计、适配、实现与验证。

## 演示准备

准备三篇可分发的公开论文和第四篇增量论文，记录下载来源、许可证/使用条件与 hash。使用专属示例数据库，不载入私人论文、凭据或真实用户 home。准备一个可讨论的研究问题与约束，标注至少一个不可直接比较的指标和一个证据不足项。

另备一份已保存成果以应对模型服务不可用，固定显示 fixture/replay；不能让录制结果冒充现场推理。live 演示需要自己的许可和预算。

## 5—8 分钟故事线

1. 展示主系统与 Research 的独立启动和数据边界图。
2. 打开项目，说明问题、约束和三篇论文；看到实际任务阶段和首行成果。
3. 点开比较单元格，对照原文，解释证据定位与语义支持的区别。
4. 展示两篇论文因评测条件不同不能直接排名，人工修正一个值。
5. 生成/打开备忘录，说明建议、未知项与下一步最小实验。
6. 加入第四篇，展示新行、受影响结论与待接受修改，旧人工判断仍保留。
7. 使用受控测试任务停止自己的 Worker，再重启，展示已提交阶段复用；主系统继续独立工作。

模型等待较长时可以打开已保存 live 成果并明确说明，不通过伪造完成进度缩短展示。

## 面试问题与可展示证据

| 问题 | 回答要点 | 证据 |
| --- | --- | --- |
| 为什么不是一个聊天页面 | 长期研究对象包含事实、人工判断和版本，需要逐项核查和更新 | 矩阵、原文、审阅和备忘录同屏流程 |
| Pi 二次开发在哪 | 显式会话资源、限定来源工具、结构化提交、取消和预算 | 一次真实工具调用及被拒绝的越界输入 |
| 怎么避免影响 RAG | 独立工程和数据、无主 RAG 调用、只读来源、Worker 限额 | 导入边界、挂载、四种负载状态回归 |
| 为何要 DBOS | 长任务有进程中断和外部请求窗口，需要阶段恢复 | SIGKILL 恢复记录，稳定任务 ID |
| 能否保证模型只调用一次 | 不能跨外部服务和本地事务保证；保证业务成果幂等并记录重放风险 | “模型已返回、提交前中断”测试 |
| 怎样保留人工修订 | 建议和审阅分开保存，ETag 并发控制，输入失效另标记 | 两个客户端编辑冲突和重跑演示 |
| 如何证明答案可靠 | 原文匹配、语义支持、可比性分开测，保留失败 | 冻结标注集与逐项结果 |
| 为什么不加更多框架 | 单机规模已有 PostgreSQL 与 DBOS 足够，先交付闭环 | 部署结构、资源预算和实际任务量 |

## 完成后的简历模板

> 基于 Pi SDK 设计并实现独立论文研究工作台，使用 React、Fastify、PostgreSQL 与 DBOS，支持跨论文证据矩阵、人工审阅和增量决策更新；设计幂等任务、阶段恢复、取消与版本并发控制，通过独立部署和资源限额建立与主 RAG 的故障边界，并完成证据质量及性能回归评测。

实际可增加的数字包括：样本论文/事实数、语义支持率、可回答项覆盖率、首行可用时间、恢复耗时、主 RAG 本地 p95 变化和用户整理时间。每个数字说明样本、模式、环境和测量口径，不填写估算的提升百分比。

未实现的功能不写进已完成成果，fixture 测试通过不写成真实模型准确率。共享硬件或提供商额度时不声称绝对零性能影响，不将整个开源主项目写成个人从零实现。
