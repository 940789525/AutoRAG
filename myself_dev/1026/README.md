## 必须看得见的效果

```text
第一轮已发送：旧消息[A 全文、B 全文]
第二轮召回：B、C
正常追加后：旧消息[A 全文、B 全文] + 新工具消息[B 的短引用、C 全文]
第三轮召回：B、D
继续追加后：此前已发送的模型消息不变 + 新工具消息[B 的短引用、D 全文]

接近容量上限：集中整理一次 → 正文可见索引重建 → 新的稳定追加阶段
整理后 B 正文已不在上下文：
  再次检索命中 B → 既有 v2 重发全文；
  read_local_evidence({ evidenceId: "e2" }) → 校验来源权限和版本后直接读完整块。
来源变化／版本不明／证据不属于当前分支 → 明确不能恢复，不用新版本冒充 e2。
```

“保留旧消息”指**实际发给模型的历史消息视图**保持稳定，仅保留原始聊天记录不足以保护 KV cache。保持前缀只是缓存可复用的必要条件；缓存开关、provider、保留时间和路由仍会影响真实命中。

## 相比 v1 的决策变化

- 废止“每次请求重新选择全部历史、相同证据保留最新位置”作为正常路径。
- 完全重复去重独立于 MMR、分差和问题类型：全量问题或启用 Rerank 也可以安全去重，前提是完整正文仍可见。
- v1 的分差／MMR 只可用于尚未发送的新本地候选，不得据此反复改写已发送历史；不是 v2 缓存去重验收的前置条件。
- 正常阶段不再拿 6000-token 软预算反复裁剪全部历史；容量紧张时才进行有阈值、有回执的集中整理。
- 首版集中压缩指确定性的历史候选正文整理，不新增摘要模型。已有 Pi compaction 要协调生命周期，不能在 context 回调里直接调用会中断当前 turn 的手动 `session.compact()`。
- 完整候选、原始工具输出、来源和引用保留；不能根据“登记过”推断“当前模型可见”。
