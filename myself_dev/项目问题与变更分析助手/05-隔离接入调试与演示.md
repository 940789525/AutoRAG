# GitHub MCP 隔离接入与调试方案

## 运行前提

本页用于之后的 P0 至 P6 实施，不代表本次已经执行接入。需要 Node.js 24 及以上、项目已有依赖、可用的对话模型认证、能够连接官方 GitHub MCP 的网络和操作者提供的读取凭据。

本方案采用官方远程服务，不需要为演示新增一个 echo 或虚构的人事 MCP。真实工具集合以接入时的 `tools/list` 为准。

当前 `.vscode/launch.json` 中“AutoRAG：仅调试 TUI（无论文收件箱）”的启动形态可以覆盖 MCP/codemode 链路，但它引用日常 `/dev-home/.autorag/config.fastembed.json` 和 `/dev-home/.pi/agent`。不得把这个入口等同于已经隔离好的 GitHub QA 环境。

本次不修改该 launch 配置。实施阶段先准备独立参数，再使用用户本地的调试配置或对隔离进程 Attach；不要为了方便直接覆盖日常配置或在共享 Pi 目录中试错。

## 隔离目录

按 AGENTS.md 优先使用受支持的 Docker QA 边界。若在现有开发容器中人工联调，也必须先隔离配置，且不能停止或重配容器里其他会话拥有的进程。

在运行项目的同一个 shell 中，先记录日常配置的绝对路径、存在状态及 SHA-256，覆盖默认配置、日常 fastembed 配置和将要涉及的日常 MCP 配置。不存在的文件记录 `ABSENT`。先保存绝对路径再隔离 HOME，防止最后只验证到新的临时 home。

随后准备任务目录。下面仅创建隔离目录并设置环境，尚未生成 AutoRAG 配置，也不会启动服务：

```bash
QA_ROOT="$(mktemp -d /tmp/autorag-github-mcp.XXXXXX)"
export AUTORAG_HOME="$QA_ROOT/autorag-home"
export AUTORAG_CONFIG="$AUTORAG_HOME/config.json"
export PI_CODING_AGENT_DIR="$QA_ROOT/pi-agent"
export PI_CODING_AGENT_SESSION_DIR="$QA_ROOT/pi-sessions"
export HOME="$QA_ROOT/home"
mkdir -p "$AUTORAG_HOME" "$PI_CODING_AGENT_DIR" "$PI_CODING_AGENT_SESSION_DIR" "$HOME" "$QA_ROOT/docs" "$QA_ROOT/evidence"
```

`QA_ROOT` 必须在整次运行中保持同一个值；新的工具 shell 不继承旧 shell 的 export。每次项目 CLI、QA 脚本或构造 AutoRAGAgent 的脚本都必须获得以上隔离变量。`--workspace` 不能替代 home/config 隔离。

## 配置准备

P1 应使用现有配置 schema 和夹具设施创建合法的 `$AUTORAG_CONFIG`，仅引用合成文档目录、独立 workspace/memory、所选模型及现有本地 embedding 配置。不要猜配置字段，也不要直接复制完整日常配置和认证文件。

保留当前本地 FastEmbed 默认路径，不为本功能切换 embedding 或重建日常索引。若实际问答路由触发了其他模型或检索调用，要记录并计入成本，不能把它们忽略后宣称“无需其他运行条件”。

操作者应通过安全环境注入提供 `GITHUB_MCP_TOKEN`；配置只引用它。不把 token 写进命令行参数、文档或 Git 文件，不打印其值。独立 Pi 目录的模型认证使用现有 `/login` 或已支持的环境凭据方式；不能自动拷贝日常 `auth.json`。

在仓库根目录，可以将以下模板复制到测试目录：

```bash
cp "myself_dev/项目问题与变更分析助手/examples/github-mcp.codemode.example.json" "$PI_CODING_AGENT_DIR/mcp.json"
```

模板中的 `${GITHUB_MCP_TOKEN}` 是 Pi 运行时展开的环境引用。它不是 VS Code 的 `${input:...}` 语法，`mcp.json` 也不应依赖 `${workspaceFolder}` 自动替换。direct 对照只使用另一份模板，其他设置保持一致。

凭据权限应按实际使用的公共仓库、PR 与 Actions 读取能力核对。只读服务设置不提升凭据原有权限；如果某个工具因权限不可用，保留实际错误并记录缺失范围，不扩大凭据权限来掩盖失败。

## 启动与最小体验

只有在上面的合法 AutoRAG 配置、模型认证和 GitHub 环境引用准备完成后，才可在同一 shell 中启动：

```bash
node src/cli/index.ts tui --config "$AUTORAG_CONFIG" --debug
```

`/mcp` 只有在相应 MCP 扩展已加载时才存在。有该命令不等于所有服务都连接成功；必须核对 GitHub 连接状态和工具目录。若命令不存在，先检查实际进程的 `PI_CODING_AGENT_DIR`、配置是否存在、是否有启用项及解析错误；不要反复换提问试图创建服务。

首次体验选一个实际可访问的 PR，替换下文占位链接：

> 请通过 GitHub MCP，使用 codemode 读取这个 PR 的标题和当前状态，只根据实际工具结果回答：`<真实 PR 链接>`。

这条问题只验证真实只读调用，不强制每次调用发现。为了单独观察冷发现，可在另一个新会话使用：

> 请先在 codemode 中发现 GitHub 服务用于读取 PR 的工具，并返回发现结果；随后通过 codemode 读取这个 PR 的标题：`<真实 PR 链接>`。不要用 bash、网页搜索或本地索引替代。

这类调试提问刻意约束路径。真实模型仍可能不遵循要求，因此只能通过实际事件判断是否成功，而不是凭它最后声称使用了 MCP。

## 业务演示

最小体验通过后，使用冻结的公开 PR 与 head SHA，发送：

> 请分析这个 PR 解决了什么问题、主要修改以及评论中的未决事项。如果该 PR 当前提交的 CI 失败，请读取相关失败日志说明失败位置。给出可核对的来源，无法读取的部分直接说明：`<真实 PR 链接>`。

演示时展示四类证据：

1. 冷会话实际看到的服务简介，以及工具发现结果；已知工具直接调用时说明这是热上下文。
2. 模型实际生成的 codemode 脚本、父调用 ID 与嵌套 GitHub 工具调用。
3. GitHub 实际返回的 PR、评论、diff 或 CI 日志，以及错误和读取范围。
4. 结果进入 EvidenceLedger 后，答案引用如何还原到原始 GitHub 链接和片段。

一般 Node 调试可观察 AutoRAG、Pi 工具管线、MCP 客户端和输入输出。codemode 脚本在 QuickJS 中执行，不能承诺普通 Node 断点能逐行调试脚本文本。可检查提交源码、嵌套事件和脚本输出，不需要为演示开发一个沙箱调试器。

不要往 MCP stdio 的 stdout 打普通调试日志；它属于协议。当前首选远程 HTTP 服务，协议边界记录也不能包含 Authorization 等凭据。

## 结果判断与排障

| 现象 | 处理 |
| --- | --- |
| `/mcp` 不存在 | 核对实际 Pi 目录及是否加载扩展；不能由此推断项目不支持 MCP |
| 服务存在但认证失败 | 记录原始错误，核对环境引用和权限，不伪造业务结果 |
| 模型用了 bash 或本地 GitHub 数据源 | 业务可能有答案，但本次 MCP 路径验证不通过 |
| 只有发现脚本，没有业务调用 | 仅完成工具发现，尚未调用 GitHub |
| 读取成功但结构化结果无引用 | 检查证据适配是否把 ID 送进脚本可见结果，以及脚本是否显式输出 |
| 日志不可读或不属于当前 SHA | 报告未验证范围，不输出“CI 正常”或已确认根因 |
| 暂停调试后超时 | 记录调试暂停影响，正常运行重试；暂停中的耗时不用于性能对照 |

## 清理与复核

退出当前任务创建的 TUI 和客户端，取消当前未完成请求，只回收当前任务拥有的进程及 `$QA_ROOT`。不停止 GitHub 服务、共享 embedding 服务、其他开发容器或其他会话。

对前面保存的日常配置绝对路径重新计算摘要或存在状态，与运行前一致后记录清理收据。需要保留的公共结果和报告写入明确指定的任务证据目录；token、完整认证文件、私人语料不能随报告保存或提交。

本目录下的示例和验收模板不能被误当成活动运行状态。以后若用户决定正式启用 GitHub MCP，应单独合并服务配置，保留原有配置项，不把整份测试文件覆盖到日常目录。
