# 项目问题与变更分析助手需求规格

## 用户问题与交付目标

开发者面对一个陌生 PR，需要分别阅读描述、关联 Issue、diff、评论和 CI 日志才能判断“为什么改、改了什么、讨论了什么、失败在哪里”。首版把这些只读查询组织进 AutoRAG 的同一会话，并保留可复核的证据。

典型输入：

> 请分析这个 PR：`<真实 GitHub PR 链接>`。说明它解决的问题、主要修改、讨论中的分歧；如果相关 CI 失败，结合实际日志说明失败位置，并提供来源。

最终答案覆盖问题背景、主要变更、讨论与未决事项、CI 状态与失败线索。没有相关 Issue、评论或失败任务时应明确说明；不能为了填满栏目编造内容。日志只支持定位失败现象时，结论应写成“日志显示”或“可能原因”，不能声称已经证明根因。

## 首版范围

| 首版交付 | 首版不做 |
| --- | --- |
| 明确的 `github.com/owner/repo/pull/number` 链接 | 企业 GitHub 域名、跨仓库全自动调查、模糊项目名解析 |
| PR 详情、diff、评论与明确关联的 Issue | 任意网页浏览、自动下载整个仓库、强制导入中央索引 |
| 与该 PR 的 head SHA 对应的 CI 状态、可读失败日志 | 重跑 CI、创建 Issue、评论、修改分支、合并 PR |
| Pi codemode 工具发现、脚本调用与结果筛选 | 自研 MCP 客户端、沙箱或通用 Agent 编排平台 |
| 有来源的回答、调用记录、direct 对照评测 | 预先承诺性能提升、跨所有 MCP 服务的通用解析器 |
| 现有普通问答和本地检索的兼容性 | 新增 embedding、数据库、后台同步服务或运行时依赖 |

本地资料与远程 PR 联合分析留作第二阶段。第一阶段先证明真实 GitHub MCP 调用、证据引用和故障反馈，避免把多数据源联邦与基本接入一起排障。

## 需求与验收要求

下列要求是拟交付标准，不是已经获得的结果。

| ID | 要求 | 验收观察 |
| --- | --- | --- |
| R01 | 复用用户级 MCP 配置接入 GitHub，只读、codemode 为默认方式 | 独立测试目录的 `mcp.json` 生效；实际工具目录和服务信息被记录；不读取项目 `.pi/mcp.json` |
| R02 | 支持真实工具发现与调用，并区分二者 | 至少一次冷会话记录发现脚本及其输出，随后出现带父调用 ID 的实际 GitHub MCP 调用；热会话允许直接使用已知工具 |
| R03 | 分析明确的 PR 及其实际关联内容 | 仓库、PR 号、head SHA 与远程结果一致；关联 Issue 有 PR 内容或接口证据，不能只按关键词猜关联 |
| R04 | 正确处理任务依赖与部分成功 | 已知身份后可并行读取 diff、评论等；日志查询必须先取得对应 run/job 身份；一个子请求失败不丢弃其他成功证据 |
| R05 | 关键结论进入现有证据引用体系 | 模型得到真实 `[eN]`；最终引用可还原为 GitHub 来源与片段，`results`、`mapping` 非伪造；不能只展示一个普通 Markdown 链接就宣称完成 |
| R06 | 调用过程可以解释和复核 | 记录父子调用 ID、工具、业务参数、结果状态、耗时、原始错误和来源；证明调用发生，不依赖最终自然语言声明 |
| R07 | 保持首版只读与既有可信配置边界 | 远程服务实际只提供选定的只读工具；写操作测试不得产生远程状态变化；不把提示词当权限边界 |
| R08 | 兼容空配置、失败与中断 | 无 `mcp.json` 时保持原工具面；401/403/限流/超时/工具错误可见；取消后不再继续派生请求或登记迟到成功 |
| R09 | 运行与验证不污染日常环境 | AutoRAG home/config、Pi agent/session 目录均隔离；记录日常配置前后摘要与测试状态清理结果 |
| R10 | 对比 direct 与 codemode 的实际效果 | 同模型、同工具集合、同任务与可比数据，报告正确率、调用、token、延迟、失败项及测量条件 |
| R11 | 不把 MCP 工具误当原检索数据源 | GitHub MCP 工具由模型通过 Pi 调用；不自动注册到 `search_all_documents`，不重复索引已有 GitHub 数据源 |
| R12 | 保持普通产品行为与已有合同 | 未使用 GitHub MCP 时不新增模型轮次、不自动维护索引；不更改已有答案与证据 schema；新增代码有对应回归验证 |

## 关键验收场景

### 明确的 PR 分析

给定一个可读取且包含变更与评论的公开 PR，用户提交明确分析请求后，系统调用真实 GitHub MCP，并返回有证据的变更说明。受控 trace 能对应模型脚本、MCP 工具执行和外部结果。

### CI 失败定位

给定一个 head SHA 和运行时间已冻结的 PR，系统只分析与此 SHA 对应的状态和任务。读取失败日志后引用失败步骤与原文，不把历史其他提交的失败或单纯的取消状态归为当前 PR 的代码问题。

### 不存在或无权读取

给定不可读取的 PR 或日志，系统保留 GitHub 返回的原始错误及已获取证据，明确哪些部分未读取。若权限或日志保留期阻断真实验证，该项为 SKIP 或 FAIL，按评测口径判断，不能报告成无问题。

### 只读请求边界

给定“分析之后帮我合并 PR”之类请求，本场景只完成分析并说明没有执行写入。GitHub MCP 的服务端只读模式和选定工具列表应使写工具不可用。该限制不等于整个 Pi 会话的 bash、其他服务或用户账号都被转换为只读。

### 普通问答兼容

没有 MCP 配置，或用户只询问本地资料时，保留当前问答、检索、索引授权和错误透明行为；不为了完成本功能增加一个全局 LLM 路由器。

## 完成定义

R01 至 R12 的对应测试、真实服务调用、真实模型运行、隔离与清理证据齐备后，才能标记本功能完成。echo 测试、预设模型或人工直接执行工具，只能证明各自覆盖的层，不能替代真实模型的业务任务成功。
