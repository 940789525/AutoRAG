# 路由规格与开发步骤

## 行为契约

| 编号 | 条件 | 必须发生的行为 |
| --- | --- | --- |
| R1 | 显式命令或完整、无歧义的操作指令 | `/index …`、完整的“查看当前索引进度”“帮我建立索引”等沿用已有快捷路径，分类调用为 0。“建立”保留 `ensure_index` 语义，由现有计划器根据就绪状态与 profile 选择 build 或 refresh。 |
| R2 | 普通输入，或需要语义判断的候选 | 已有普通问答快速路径直接传递全文；其余含“索引”等现有候选信号的输入最多做一次分类。关键词只触发判断，不授权操作。不要求为“文件／资料库／收录”的每种改写添加规则。没有候选信号的改写仍可通过普通问答查询。 |
| R3 | 候选分类完成 | 明确要求建立、重建、刷新或取消任务时，保留配置、约束、作用域、任务所有权和待澄清校验。查询、讨论、否定或引述操作指令等只读意图返回普通问答。特别是候选被模型判为 `operation/status` 时，也交回全文；只有 R1 的专用状态入口可以直接用状态结束本轮。 |
| R4 | 当前有效候选的分类超时、输出无效、提供方报错 | 保留底层诊断，清理失效的待确认状态，回到正常问答，不授予索引写权限，不自动重试分类。若用户确实希望操作而意图仍无法确定，正常回答可以简短澄清。原话只记一次，正常回合最多启动一次。 |
| R5 | 用户按 Esc、关闭会话、或更新的输入替代当前分类 | 取消优先，迟到结果不得执行、重新发问或覆盖下一条输入。对于“先重建，再总结”等包含实际写操作的复合指令，保留现有拆分澄清；对于“先列文件，再看是否均已建索引”等纯查询，不得只因连接词触发操作澄清。 |
| R6 | 用户询问文件及其索引覆盖 | 正常回答同时给出文件清单和可核实的索引状态，或明确哪部分无法核实。仅有 `ready: true`、最近任务成功、或检索命中若干条，均不足以声称全部覆盖。 |

## 建议开发顺序

1. **先改分类决策。** 在 [index-intent.ts](../../src/agent/index-intent.ts) 的 `classifyIndexInput()`、分类提示和 `handle()` 中实施 R1–R5。沿用现有结构化结果；在运行时区分来自整句快捷规则的 `status` 和来自候选模型的 `status`，避免模型偶尔误判时仍吞掉整句。把纯查询与真正的写入复合指令区分开。分类提示只需少量对照例（查现状、明确执行、引述或否定），保留现有输出上限。
2. **接回现有问答。** [agent.ts](../../src/agent/agent.ts) 的 `routeInteractiveInput()` 已能在路由返回 `false` 时调用 `routeOrdinaryInput(input, pi, true)`。复用这个入口，遵守现有 steer／排队规则；不要另行提交一条扩展消息代替用户原话。失败处理须区分“本次识别失败”与“本次请求已撤销”：后者即使也抛出异常，仍应消费旧输入。保留可追溯的错误文本，不能仅靠显示一条 `triggerTurn: false` 的通知就结束有效提问。
3. **指导正常回答取得只读证据。** 在现有回答指导中说明怎样用已有目录读取／`bash` 能力进行核对。只在用户询问覆盖时，在允许的本地根和 scope 内枚举实际文档，用活动 `ready.json` 指向的 profile，按项目虚拟 source ID 比对 `journal.sqlite` 的 `sources`。以只读方式打开现存数据库；[IndexJournal 构造函数](../../src/indexing/journal.ts) 会建目录、建表，不能用作只读入口。遵守原有权限；不可读、截断、profile 切换或无法可靠核实时，保留诊断并限制结论。区分“已登记”和“内容已同步至最新”。不得通过 `bash` 调用 CLI 建索引来“验证”，也不应在每个问题前附加清单或文档正文。[索引就绪校验](../../src/indexing/pipeline.ts) · [虚拟文件标识](../../src/filesystem/source-paths.ts) · [状态工具](../../src/agent/index-controls.ts)

## 调用预算

按**每条输入的应用层调用**计数：完整命令、普通快速路径为 0 次索引分类；候选最多 1 次，包括失败，不新增第二个分类器、第二次判断或自动重试。问答模型和已有工具循环另计，工具轮数会因实际问题和权限而变。分类请求保持短文本和必要状态，排除文件清单与正文；覆盖核对只向回答模型返回必要的名称、状态、计数或缺失原因。沿用现有 12 秒识别上限，最慢候选仍可能先等待一次超时。真实 token、延迟和节省量需要实测。
