## 已证实的问题与原因边界

### 分块前的解析结果已经失真

解析清单显示两份文件均由 `kordoc 4.24.19` 解析。本科成绩单的 Markdown 全文为 2,015 字符，研究生成绩单为 801 字符；两份全文均没有完整的“体育”二字。本科成绩单解析时间为 09:20:15，研究生成绩单为 09:25:56，均早于查询。课程名称混有不成词的汉字、拉丁字符及表格分隔符，难以将课程与分数可靠对应。

因此，可以确定课程信息没有被解析文本有效保留。具体损伤来自 OCR 识别、页面图像质量、文字层处理还是表格布局还原，需要继续对照原始页面、OCR 中间结果与最终 Markdown 才能确定。尚不能将故障定位到某一个 OCR 引擎或某一段切块代码。

### 索引登记与召回未保证可用证据

两份成绩单的全部 4 个索引块均被召回，但内容不足以回答问题；`read_local_evidence` 的 `complete: true` 只表示完整读取指定块，不代表识别准确或覆盖整份原件。

本例暴露出解析质量与索引成功状态之间的缺口：失真文本仍进入活动索引，登记成功与查询时空的 `diagnostics` 没有表达课程表格的可读性问题。这不等于已经证明现有所有解析诊断均缺失，而是说明本例中的失真未被有效反映。

检索还返回了 46 个论文块，增加无关数字和表格噪声。它是次要问题；成绩单块已经全部召回，单纯提高 topK 或调整排名不能恢复解析阶段丢失的课程名称。

### 原件核读依赖用户再次提示

第一轮检查集中于系统命令和系统 Python，没有发现已安装的 Node PDF 工具；第二轮使用同一容器内已有的 PDF.js 与 Canvas 即完成渲染。由此可见，第一轮的工具失败不足以支持必须重新上传截图的结论。原件核读的发现与执行路径不够可靠。

第一轮 bash 脚本还对 `pdfinfo`、`pdftotext` 使用了 `2>/dev/null`，且管道未启用失败传播，导致没有取得内容时工具整体仍返回 `isError: false`。空输出和工具执行标记应结合实际返回内容判断，不能视为成功读取。

系统缺少 `tesseract` 命令不能证明索引 OCR 未运行：项目另有基于 `tesseract.js` 的解析路径。开关、引擎选择和实际识别质量是三个不同问题，参见 [解析器配置](../../src/parser/defaults.ts) 与 [OCR 实现](../../src/parser/ocr-engines.ts)。

## 修复后的验收条件

1. 用可公开的合成图片型成绩单建立固定参考答案，覆盖多学期、多列课程、相邻数字列与跨块表格。分别核对解析全文、分块内容与最终答案，确保课程名、成绩及其对应关系保留正确。
2. 对无可提取文字层、识别失真或表格关系不可信的输入，提供可追踪的诊断或核读路径；不能仅凭任务成功、非空文本和块数宣称内容已正确识别。质量判断规则需要通过上述样本验证，不将非空或固定字数当作准确性标准。
3. 在既有容器环境中，用第一轮原话即可完成原件核读或说明实际阻塞，不依赖第二次“使用已有 PDF 工具”的提示，不要求用户重复提供已经可读取的原件。
4. 原件核读结果保留来源、页码及必要的位置依据，课程与成绩能够逐项对照参考答案。若仍无法确认，明确说明未确认项；原件核读成功不能被报告为已有索引已修复。
5. 工具失败保留底层错误，避免通过 stderr 重定向和管道状态掩盖失败。复验限定于隔离配置和合成材料，不修改日常配置、原始成绩单或其他会话进程。

以上为行为验收边界，不预先指定新依赖、OCR 引擎或图像分块方案。针对文本型 PDF、独立图片、Excel 等格式的能力结论，需要各自的样本验证。
