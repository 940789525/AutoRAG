# 接入与开发步骤

## 1 接入位置

下表中的现有路径相对仓库根目录。新增文件名为建议；开发前重新核对本地接口。

| 位置 | 当前职责 | 下一步工作 |
| --- | --- | --- |
| `src/agent/index-controls.ts` | 命令解析、工具、粗粒度意图规则、TUI 进度 | 保留显式命令和进度；替换旧自然语言许可来源；使原生工具接受具体请求校验 |
| `src/agent/agent.ts` 的 `routeInteractiveInput()` | 在普通问答前检测索引输入 | 接入本地分流、候选异步识别、待澄清状态和内部操作分发 |

| `src/agent/agent.ts` 的 `indexOperations()` 与 `startIndexJob()` | 参数校验、服务准备、启动任务、候选激活 | 暴露必要只读状态；接收解析完成的请求；保留锁与最终检查 |
| 建议 `src/agent/index-intent.ts` | 新增纯逻辑 | 本地分类、结构化 schema、参数解析、计划与状态转换；过大时再拆分 |
| 建议 `src/agent/index-intent-model.ts` | 新增薄适配层 | 复用现有对话模型完成一次无工具的结构化判断 |
| `src/indexing/jobs.ts` | 任务生命周期、幂等和所有权 | 优先直接复用；只有明确接口缺口才修改 |
| `src/indexing/pipeline.ts` | 指纹、分块、缓存、向量写入、候选切换 | 复用行为与报告；本任务不重写管线 |
| `src/agent/query-routing.ts` | 可选 Jev 问答路由 | 保持原行为，不作为新增识别前置条件 |

## 2 输入调度的具体实现

当前 `AutoRAGPiInteractiveRuntimeOptions.onInput` 返回同步 `AutoRAGInputDisposition`，input hook 也同步消费结果。不能简单在 `routeInteractiveInput()` 中加入 await 而不调整调用方。

优先方案：将 onInput 契约允许返回 Promise，input hook 使用 async 并等待结果；本地普通路径内部不调用模型。先确认当前 Pi 的 input 扩展契约支持异步返回，再修改类型和测试。若该版本不支持，应先返回 handled，在内部串行调度候选解析；两种方式择一实现，不同时保留两套入口。

每次候选识别绑定输入序号、会话版本和 AbortSignal。用户取消、替换请求或会话关闭后，旧结果失效。需要覆盖“旧请求模型较慢、新请求先完成”的顺序，不能由到达时间覆盖最新请求。

### 搜索正在执行时

现有自然语言分支受 `state.run === undefined` 限制，这会让索引控制输入进入搜索 steering/follow-up。新入口必须先进行操作候选分流，再决定是否走原有搜索输入路径。

- 已注册 `/index` 命令沿用 Pi 命令机制；不要二次解析或重复提交。
- 明确 status/cancel 等请求进入独立内部任务路径，不能被当成搜索修正。
- 候选识别不能在同一个正流式生成的 Pi 会话里直接发起竞争性的 `session.prompt()`；使用薄适配层调用同一已配置模型，独立 AbortSignal，无工具。
- 候选被判为普通输入后，按它原来的 Enter/Alt+Enter 语义进入 steering 或 follow-up，保持原文、附件和顺序。
- 索引提交仍遵循现有资源限制与写锁。忙碌时报告任务状态或原因，不自行停止其他进程。

增加模型调用前，先验证所用模型凭据解析与正常对话一致，不把 Jev 的独立认证路径带入该功能。

## 3 受限操作如何执行

建议将规则或模型的结果先解析为同一种内部请求，然后直接调用现有操作适配层：

```text
文本 → GateDecision → 必要时 ModelDecision
     → 参数解析 → 只读状态计划 → 最终校验
     → startIndexJob / jobs.status / jobs.cancel
```

该路径不需要为了“选择一次工具”再进行额外模型回合。保留原生 `manage_local_index` 时，同样检查具体请求许可；普通问答回合仍不能任意调用 build/refresh/cancel。

初次版本可将状态计划放在现有控制模块旁的纯 helper 中，不必新增通用 Plan/Executor 框架或持久计划数据库。

`startIndexJob()` 的已有最终校验必须保留：全部本地根范围、profile、远程消费者授权、写锁、候选代激活。不能因为上层检查过就移除。请求 ID 复用任务模块的幂等机制，避免快速双击或迟到回调重复构建。

## 4 分阶段开发

### 第一步 固化行为样例和本地规则

- 先把 04 的核心样例变成表驱动测试，覆盖旧缺陷。
- 引入 ordinary/explicit/candidate 三态结果，删除关键词直接授予写权限的逻辑。
- 实现少量完整句式，含 build 与 rebuild 的目标区分。
- 保留所有显式 `/index` 命令行为。

完成条件：规则结果可解释；咨询、否定和引用不能误授写权限；候选不执行任务。

### 第二步 接入按需模型识别与澄清

- 复用对话模型和凭据，构造一次短结构化识别。
- schema 校验、超时、取消、错误透明显示；无模型时给出命令替代。
- 增加单项待处理请求和参数修正；对普通新问题清除旧许可。
- 接入异步 input 契约并验证流式搜索期间的输入顺序。

完成条件：正常普通输入没有新增模型识别调用；候选只进行一次应用层识别；无有效判断不启动写任务。

### 第三步 接入状态计划与受限执行

- 提取必要的只读索引快照，解析 scope/profile/job。
- 映射 ensure_index/rebuild/refresh，处理首次建立、切换 profile 和限制冲突。
- 统一内部调用与原生工具的请求校验；绑定 requestId 和会话版本。
- 复用进度和报告，让用户看到选择的操作、profile、范围及原因。

完成条件：选对操作和范围，普通问答不触发索引准备；失败或取消保持既有候选保护语义。

### 第四步 评测与交付

- 运行规则、模型和入口集成测试；用隔离配置和合成文档验证真实模型路径。
- 进行旧正则与新方案对照，报告错误执行、漏识别、模型调用率和延迟。
- 更新用户说明与 1030 的对应自然语言要求。
- 提交实现与验收结果记录，明确真实模型、版本、样本量、失败和跳过项。

完成条件：满足 04 的门禁；未达到指标时先分析候选召回、模型理解还是状态解析出错，不能仅报告总准确率。

## 5 可观测性和成本

每次输入记录最少的结构化诊断：

- 本地命中 ruleId、分支、是否调用识别模型。
- 识别耗时、实际模型请求次数、可获得的 token 用量。
- 意图、参数缺失或校验失败原因；最终操作和对应 jobId。
- 计划原因和 IndexReport 的真实处理计数。

不需要默认另建包含用户全文的持久日志。优先复用既有诊断和任务报告；评测明文仅使用合成输入。原始底层错误仍应向操作者如实显示，不以固定错误枚举替换详情。

新增平均识别开销可以按以下口径估算：

```text
全部请求新增平均开销 ≈ 本地分流开销 + 候选比例 × 候选模型识别平均开销
```

该式不是 P95 公式。需要单独测整体、普通问题和候选问题的延迟分布。即使普通问题被误召回，也会产生一次额外调用，必须计入普通问答成本。

Jev 开启与关闭分别评测，所有对照保持相同配置；不得通过只在新方案关闭 Jev 制造提速。分类调用为 ordinary 后仍需原有问答模型回答，不能宣称这类输入完全没有额外回合。

## 6 开发环境约束

代码开发遵守仓库 AGENTS.md 的分支和检查要求，不创建 worktree。目录中方案文件的存在不等于已经授权部署或合并。

所有 manual QA 使用临时 `AUTORAG_HOME` 与 `AUTORAG_CONFIG`，优先使用项目已有 Docker QA 边界。使用合成资料，不向远程模型发送真实文档正文；不修改共享真实 home，不启动或重启日常容器，不停止其他会话的服务。真实配置按仓库要求记录前后哈希。

本次文档编写不执行模型下载、索引构建或运行配置变更。后续新增运行时依赖或更换 embedding 后端仍需按仓库规则另行确认。
